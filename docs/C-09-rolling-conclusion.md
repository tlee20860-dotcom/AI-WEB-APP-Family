### 議題 1：編號規則（✅ 已結論）

#### 1.1 核心原則

| # | 原則 |
|---|---|
| 1 | 編號完全自動生成，用戶不選擇、不輸入 |
| 2 | 編號在 UI 上完全隱形，用戶零負擔 |
| 3 | 編號一旦生成，永久不變 |
| 4 | 名稱可改，編號不動 |

#### 1.2 編號格式

> **{大類}-{子類}-{序號3位}**
> 無子類時：`{大類}-{序號3位}`

#### 1.3 大類前綴

| 大類 | 前綴 |
|---|---|
| 成員 | MEM |
| 支付方法 | PAY |
| 銀行帳號 | PAY-BANK-{碼}-{類型} |
| 保單 | POL |
| 保險基金 | FUND-INS |
| 獨立基金 | FUND |
| 支出類別 | CAT |
| 支出項目 | ITEM |
| 保險公司 | COMP |
| 收入 | INC |
| 銀行交易 | TXN |

#### 1.4 子類短碼

| 子類 | 短碼 | 範例 |
|---|---|---|
| 保單-基金投資型 | FUND | POL-FUND-001 |
| 保單-普通保險 | NORM | POL-NORM-001 |
| 保單-基金保險 | FUNIN | POL-FUNIN-001 |
| 保單-儲蓄型 | SAVE | POL-SAVE-001 |
| 支出-學校類 | SCH | CAT-SCH-001 |
| 支出-交通類 | TRA | CAT-TRA-001 |
| 支出-醫療類 | MED | CAT-MED-001 |
| 支出-銀行類 | BNK | CAT-BNK-001 |
| 支出-其他 | OTH | CAT-OTH-001 |

#### 1.5 支付方法樹狀結構

> 支付方法（PAY）
> ├─ 銀行類（PAY-BANK）
> │   ├─ 中銀
> │   │   ├─ 家庭共用帳號（PAY-BANK-BOC-FAM-001）
> │   │   └─ 個人帳號（PAY-BANK-BOC-PER-001）→ 所屬：老公
> │   └─ 匯豐
> │       └─ 家庭共用帳號（PAY-BANK-HSB-FAM-001）
> ├─ 現金（PAY-CASH-001）
> └─ PayMe（PAY-PAYME-001）

#### 1.6 用戶操作流程

> 所有新增實體：
> 欄位：[已選值 ▼] [+]
>        ↓
>     點 + 號 → 輸入名稱 → 自動生成編號 → 自動選中

#### 1.7 保單與關聯基金（同介面）

| 項目 | 說明 |
|---|---|
| 保險基金 | 只能在保單編輯頁新增 |
| 獨立基金 | 獨立新增 |
| 修改關聯基金 | 進保單編輯頁 |

#### 1.8 下拉選項管理

| 操作 | 入口 |
|---|---|
| 新增 | 欄位旁 + 號 |
| 編輯 / 刪除 | 基礎資料庫（改名為「編號對照清單」） |
| 編號對照清單 | 統一管理所有編號 |

| # | 情境 | 編號 | + 號 |

| 1 | 成員 | MEM | ✅ |

### 議題 2：編號生成與儲存細節（✅ 已結論）

#### 2.1 核心設計：無計數器，用推導

| 項目 | 做法 |
|---|---|
| 編號儲存 | 實體自己的節點（`funds/{id}/code`） |
| 計數器節點 | 不需要 |
| transaction | 不需要 |
| 生成方式 | 查現有實體最大序號 + 1 |

#### 2.2 生成演算法

> **generateCode(prefix, 現有實體列表)：**
> 1. 過濾出所有 code 以 `{prefix}-` 開頭的實體
> 2. 提取序號部分（001, 002, ...）
> 3. 取最大值 N
> 4. 回傳 `{prefix}-{N+1 補零到3位}`
> 5. 檢查是否重複 → 若重複，提示用戶重試

#### 2.3 序號範圍

| 項目 | 做法 |
|---|---|
| 範圍 | 每家庭獨立（各家庭從 001 開始） |
| 位置 | `families/{familyId}/funds/` 等節點 |
| 刪除後 | 不重用（跳號可接受） |

#### 2.4 子類短碼決定

| 情境 | 短碼來源 |
|---|---|
| 保單-基金投資型 | 依 `type='fund_insurance'` 自動帶 `FUND` |
| 支出-醫療類 | 依 `category.shortCode` 決定 |
| 保險基金 | 依上下文自動帶 `FUND-INS` |

> 用戶永遠不用選。

#### 2.5 併發衝突處理

| 情境 | 風險 | 對策 |
|---|---|---|
| 兩個裝置同時新增 | 拿到同一號 | 重複檢測 → 提示用戶重試 |
| 網路斷線重試 | 號碼跳號 | 可接受 |
| 刪除後再新增 | 是否重用舊號 | 不重用 |

> **核心決策**：家庭系統併發機率極低，不引入 transaction 複雜度，用「重複檢測」補救。

#### 2.6 為什麼不用計數器？

| 對比項 | 計數器方案 | 推導方案 |
|---|---|---|
| Firebase 節點 | 需額外 `counters/` | 不需 |
| 生成邏輯 | 需 transaction | 純查詢 |
| AI 理解 | 需懂計數器 + transaction | 只需懂「查最大 + 1」 |
| 崩潰風險 | 計數器損壞 → 全站編號失效 | 無額外依賴 |
| 維護成本 | 需同步 | 零 |

### 議題 3：編號查詢與反查（✅ 已結論）

#### 3.1 從編號查實體

| 項目 | 做法 |
|---|---|
| 決策 | 遍歷實體列表，比對 code |
| 原因 | 對齊議題 2「無索引」；實體數量少，成本低 |
| API | `getEntityByCode(familyId, entityPath, code)` |
| 使用場景 | 新增後自動選中、顯示時解析名稱 |

#### 3.2 從名稱查編號

| 項目 | 做法 |
|---|---|
| 決策 | **不做**（日常不需要） |
| 原因 | 編號 UI 完全隱形，用戶不會用名稱查編號 |
| 例外 | 舊資料遷移時才需要（留給議題 4 處理） |

#### 3.3 從編號展開關聯

| 項目 | 做法 |
|---|---|
| 決策 | 即時遍歷所有實體，找出引用此編號的 |
| 原因 | 對齊議題 1.5（支付方法樹狀）與 1.7（保單關聯基金） |
| API | `getRelatedEntities(familyId, code)` |
| 使用場景 | 保單詳情顯示關聯基金、支付方法樹狀展開 |

#### 3.4 實際 API 清單（`id-resolver.js`）

| API | 用途 |
|---|---|
| `getEntityByCode(familyId, entityPath, code)` | 從編號查實體 |
| `getRelatedEntities(familyId, code)` | 從編號展開所有關聯 |

> 「從名稱查編號」不在此模組。

#### 3.5 新增：編號對照清單頁（取代基礎資料庫）

| 項目 | 內容 |
|---|---|
| 頁面名稱 | 編號對照清單（原「基礎資料庫」） |
| 功能 | 列出所有編號、編輯名稱、刪除實體 |
| 不做新增 | 新增走欄位旁 + 號 |
| 使用場景 | 用戶需要查看 / 編輯 / 刪除編號時 |

#### 4.1 遷移範圍

| 類別 | 是否遷移 |
|---|---|
| 保單 | ✅ |

| 成員 | ✅ |

| 銀行交易 | ✅ |
| 保險公司 | ✅ |
| 銀行帳號 | ✅ |

**全部遷移。**

#### 4.2 舊 ID 處理

| 項目 | 決策 |
|---|---|
| 是否保留 legacyId | **不保留** |
| 原因 | 舊 ID 是隨機 push key，不可讀；保留會違背「消除相容層」核心目標 |

#### 4.3 遷移工具形態

| 項目 | 決策 |
|---|---|
| 形態 | **C+**：AI 生成 JSON + 系統內建匯入按鈕 |
| 原因 | 複用之前 portfolio 匯入功能，已驗證可行 |

#### 4.4 遷移流程

| 步驟 | 誰 | 動作 |
|---|---|---|
| 1 | 你 | 從 Firebase Console 匯出 JSON |
| 2 | 你 | 上傳給 AI |
| 3 | AI | 分析舊結構，推導保單已供金額 / 期數 / 月供 / 年費 |
| 4 | AI | 產出新格式 JSON（含自動生成編號） |
| 5 | 你 | 貼回系統匯入 |
| 6 | 你 | 其他支出重新輸入 |

#### 4.5 對齊議題 1~3

| 項目 | 對齊點 |
|---|---|
| 編號生成 | 依議題 2「查最大 +1」規則 |
| 用戶零負擔 | 遷移時只需上傳 JSON |
| 編號對照清單 | 遷移後可查看所有編號 |
| 無相容層 | 不保留 legacyId |

#### 4.6 AI 需推導的保單欄位

| 欄位 | 推導方式 |
|---|---|
| 已供金額 | 由 `insurance_payments` 統計 |
| 已供期數 | 由 `insurance_payments` 的月份數量 |
| 月供金額 | 直接讀 `monthlyPremium` |
| 年費 | 直接讀 `annualPremium` |
| 開始年度 | 直接讀 `firstStartYear` / `firstStartMonth` |
| 剩餘期數 | 總期數 − 已供期數 |

#### 4.7 新格式包含

| 項目 | 內容 |
|---|---|
| 每個實體的 `code` | 例如 `FUND-001`、`POL-NORM-001` |
| 保單的完整推導結果 | 已供金額 / 期數 / 剩餘期數 |
| 基金的快照 | 從舊 `snapshots` 轉為 `{dateKey}` 格式 |
| 舊代碼映射 | 狀態等舊值 → 新編號（一次性記錄） |
